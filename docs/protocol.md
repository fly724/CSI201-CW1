# 应用层协议候选方案

状态：**设计草案，尚未实现或承诺完全兼容附录**。依据为 Protocol Reference 第 1–7 页；附录是参考示例，任务书第 3 页允许团队自定协议。

可采用以下方案作为起点：

- 每客户端保持一个 TCP 连接；4 字节网络字节序无符号长度前缀，再接 UTF-8 JSON 对象，长度按字节计算。
- 候选负载范围 1–65,536 字节；接收缓冲区保留半帧，并循环拆出合并到达的多个完整帧。
- 信封采用 `version`、`type`、`request_id`、`event_id`、`session_id`、`payload`；请求和响应关联，异步事件单独编号。
- 消息涵盖登录、目录、房间、成员、准备、开赛、答题、排行榜、离开和注销；事件涵盖成员变化、关闭房间、开赛、出题、题目结果和结束。
- 区分响应、事件与错误；帧无法安全恢复时只关闭受影响连接。
- 单调时钟决定答题截止；服务器控制题序、答案接受与计分。关闭前不能披露答案。
- 共享状态需要明确所有权及同步方式，不能在持有全局锁时进行可能阻塞的发送。

实现前必须补全：

1. 每种消息的完整字段、类型、长度、必需性、响应及错误码；附录没有完整列出所有响应，不能直接当作完整规范。
2. 会话生成、绑定连接、注销和重复请求规则。
3. 重复身份、房主离开、开赛门槛、准备撤销、房间容量及房间销毁策略。
4. 是否在全部活跃玩家答题后提前关题，截止边界如何判定，断连后如何改变参与集合。
5. 排行榜同分排序、离开者成绩和最终结果保留规则。
6. 并发模型、锁与状态所有权、发送超时、背压和 Ctrl+C 清理。
7. 请求/响应/事件示例、状态转移、版本兼容及配对验证。

最终设计必须写入 Development Documentation；仅引用附录不能替代团队自己的协议文档。
